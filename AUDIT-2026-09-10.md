# FreeTradeJournal project audit

Audited 10 September 2026, repository revision `3cc046e`. Application code and dependencies were not changed. This report and its supporting evidence are the only retained changes.

The highest priorities are preventing lost trades during overlapping sync writes, removing authentication codes from telemetry, and making account deletion reliably stop billing and remove data. The existing test suite passes, but important failure paths are uncovered.

## Scope and verification

Reviewed authentication and authorization boundaries, Firestore/Storage rules, Stripe checkout/webhooks, AI quota enforcement, public API proxies, cloud sync, local persistence, deletion, import processing, analytics, build configuration, and test coverage. Inspected React loading and bundle structure using the React performance guidance.

No production database, payment, email, push, or account mutations were performed. No live exploit was attempted. This is a broad repository audit, not certification of every route or a complete visual/accessibility or SEO audit. A dedicated Git-history secret scanner was unavailable; the credential scan has narrower coverage.

## High priority

### H1 — Password-reset codes are passed to analytics

**Locations:** `src/components/PostHogTracker.tsx:50`, `src/lib/analytics.ts:26`, `src/App.tsx:104`, `src/pages/ResetPassword.tsx:15`.

The tracker runs on public authentication routes and explicitly captures `window.location.href`. Google Analytics initialization does the same. The reset page takes the bearer reset credential from `?oobCode=...`. Opening a valid reset URL therefore passes that credential into telemetry before the password is changed. The PostHog path does not require analytics consent. Anyone with access to the resulting telemetry could obtain a still-valid reset code; actual retention or misuse was not checked.

**Proposed change:** Exclude authentication-action routes from telemetry and redact query strings/fragments centrally, including SDK automatic URL/referrer properties and exceptions. Keep the reset code in page memory while removing it from the address bar before telemetry starts. Review existing analytics records for exposure without copying codes into tickets or logs.

```ts
// Before
posthog.capture('$pageview', { $current_url: window.location.href });
// After: minimum explicit-event protection; also apply SDK-wide redaction.
if (!['/reset-password', '/verify-email'].includes(location.pathname)) {
  posthog.capture('$pageview', {
    $current_url: window.location.origin + location.pathname,
  });
}
```

### H2 — Overlapping saves can permanently overwrite newer trades

**Locations:** `src/services/sync-engine.ts:375`, `src/services/sync-engine.ts:394`, `functions/src/index.ts:5349`.

`syncKey` sends entire collection snapshots immediately. There is no per-key serialization, revision check, or compare-and-swap on the server. The `writingKeys` set suppresses polling temporarily but does not order writes. If save B finishes before older save A, A becomes the cloud value. Both clear the dirty flag; a later poll replaces the latest local collection with A.

**Reproduced:** two pending writes, completed newest first, followed by a poll: the newly added trade disappeared locally. This can also occur between devices even after adding a client-side queue.

**Fix:** Serialize/coalesce writes per user/key, acknowledge only the corresponding local revision, and enforce server-side revision conflicts. Prefer record-level operations with versions for trades and journals. Test delayed/reversed writes, failures, two devices, and logout during an in-flight save.

### H3 — Sync resurrects deliberate deletions

**Locations:** `src/services/sync-engine.ts:92`, `src/services/sync-engine.ts:179`, `src/services/sync-engine.ts:297`, `src/lib/account-merge.ts:95`, `src/utils/user-storage.ts:56`.

Dirty collections are merged by union of IDs. The merge cannot distinguish a record deleted locally from a record created remotely, so it restores deleted records. Separately, clean devices ignore remote empty arrays, even after the server accepts a deliberate delete-all. Offline empty writes are not marked dirty either.

**Reproduced:** deleting one of two trades offline restores it on reconnect. A clean device retaining one trade ignores remote `[]`.

**Fix:** Persist deletion tombstones or record-level delete operations with revisions; distinguish initial empty seeds from authoritative empty snapshots. Do not remove the existing safety guards without replacing their protection against stale-device overwrites.

### H4 — Account deletion can succeed while subscriptions keep charging

**Location:** `functions/src/index.ts:5461–5480`, followed by Auth deletion at line 5588.

Stripe cancellation failures are logged and ignored. The function then deletes the user document and Auth identity and returns success. A transient Stripe failure can leave an active subscription charging someone who can no longer sign in to manage it. Only one subscription-list page is inspected, and the cancellation filter also omits some non-terminal statuses.

**Fix:** Use a durable deletion job: disable access, record billing identifiers, enumerate all subscriptions, confirm cancellation, retry incomplete cleanup, then finalize deletion. Do not report completion until billing cancellation is confirmed.

```ts
// Before
catch (err) { console.error(err); /* continue deleting identity */ }
// After — design sketch
catch (err) {
  await deletionJob.update({ stage: 'billing_pending' });
  throw new functions.https.HttpsError('unavailable', 'Account deletion is pending billing cleanup.');
}
```

### H5 — Account deletion misses private testimonials and MetaTrader data

**Locations:** `functions/src/index.ts:1590`, `functions/src/index.ts:5485`, `functions/src/index.ts:5522`, `functions/src/index.ts:5958`.

New testimonials store UID/email in `testimonialsPrivate`, while public testimonial documents omit UID. Deletion queries the public collection by UID, so it finds neither the new public testimonials nor their private identity records. The hard-coded subcollection list also omits `mtIngest` and `mtSync`, which contain broker deals and account identifiers. Deleting the parent user document does not remove those subcollections. Other cleanup failures are swallowed before success is returned.

**Fix:** Query private testimonial records by UID and delete both documents by their shared ID. Use a retryable recursive user-subtree cleanup with an explicit policy for separate collections.

```ts
// Before
db.collection('testimonials').where('uid', '==', uid);
// After — query the actual ownership records, then batch/paginate paired deletes
db.collection('testimonialsPrivate').where('uid', '==', uid);
// Delete testimonials/{id} AND testimonialsPrivate/{id} for every result.
```

### H6 — Push subscriptions allow backend requests to arbitrary HTTPS destinations

**Locations:** `functions/src/index.ts:2251`, `functions/src/index.ts:2367`.

Any authenticated user can register an arbitrary endpoint and generated subscription keys. The daily worker passes the endpoint directly to `web-push`, which constructs an HTTPS request to its hostname/port/path. No provider-host allowlist, subscription count cap, or registration rate limit is enforced. Send calls have no explicit timeout and are processed sequentially.

**Locally verified:** `web-push.generateRequestDetails` accepts `https://127.0.0.1:8443/audit-only` and creates POST request details. No request was sent. Production network reachability and TLS requirements limit which internal services would actually be reachable; credential theft was not demonstrated.

An attacker can direct backend requests to an attacker-controlled HTTPS host, retain many subscriptions, and delay the reminder job. Internal targeting is a server-side request forgery risk where routing and TLS permit it.

**Fix:** Validate exact trusted push-provider hostname rules, HTTPS/default port, key lengths and encoding; reject credentials/private destinations; cap and rate-limit registrations; set per-send deadlines and a true per-subscription send budget.

```ts
// Before
await webpush.sendNotification(subscription, payload);
// After — helpers must validate actual supported provider domains
assertTrustedPushSubscription(subscription);
await webpush.sendNotification(subscription, payload, { timeout: 5000 });
```

### H7 — Vulnerable spreadsheet parser processes imported files

**Locations:** `package.json:71`, `src/utils/csv-parser.ts:2248–2254`.

The project uses `xlsx` 0.18.5 and passes uploaded workbooks to `XLSX.read` in the browser. This reaches the file-reading surface affected by SheetJS prototype-pollution and regular-expression denial-of-service advisories. A crafted file a user imports can freeze parsing; this audit did not demonstrate script execution. The official fixes are 0.19.3+ and 0.20.2+ respectively. [SheetJS prototype-pollution advisory](https://cdn.sheetjs.com/advisories/CVE-2023-30533), [SheetJS ReDoS advisory](https://cdn.sheetjs.com/advisories/CVE-2024-22363).

**Fix:** Replace the obsolete npm distribution with a reviewed, pinned official release covering both advisories, or another maintained parser. Run parsing in a worker with termination, size, and row limits. `npm audit` reports no fix available for the current npm package.

```text
Before: xlsx 0.18.5 from the npm distribution
After: reviewed, pinned official SheetJS release >=0.20.2,
       with artifact integrity and broker-import regression checks
```

## Medium priority

### M1 — Sync retry limit never takes effect

**Location:** `src/services/sync-engine.ts:154` and its catch/retry block.

Every `enable()` call resets `retryCount` to zero; retries call `enable()` again. Repeated failures consequently retry every second forever, never reach the terminal fallback, and never mark the initial pull finished. **Reproduced:** six pulls in five seconds despite `maxRetries = 3`.

**Fix:** Reset the counter only on a new explicit start or successful connection. Stop retries after disable and mark initial loading complete on terminal failure. Retry reconnection deliberately rather than continuously reporting attempt 1/3.

### M2 — Deleting one user's data deletes other users' local screenshots

**Locations:** `src/utils/image-store.ts:46`, `src/pages/Settings.tsx:354`, `src/pages/Settings.tsx:377`.

Screenshots from every signed-in identity share the same `ftj-images/images` object store. Both deletion flows call `clearAllImages()`, which clears the entire store. On a shared browser, user B clearing data permanently removes user A's locally stored screenshots, while A's journal entries still reference them.

**Fix:** Scope image records by UID and delete only that user's records. Migrate existing records using journal ownership before implementing scoped deletion.

### M3 — Extra query parameters bypass public API cache reuse

**Locations:** `api/twelvedata/[...path].ts:29`, `api/finnhub/[...path].ts:43`, `api/fred/[...path].ts:37`; similar pattern in GIF/news routes.

Handlers allowlist forwarded parameters but silently ignore unknown incoming parameters. Requests such as `?symbol=EUR/USD&nonce=1` and `&nonce=2` generate the same upstream request but distinct function URLs. Vercel uses request URLs in function cache keys; ignoring parameters inside the handler does not normalize those keys. With no application-level shared cache or rate limit, anonymous callers can consume upstream quotas and degrade legitimate market-data access. Any separately configured production firewall was not inspected. [Vercel cache-key documentation](https://vercel.com/docs/caching/cdn-cache/purge).

**Fix:** Reject unknown/duplicate parameters and unsupported methods, canonicalize valid inputs, and use shared upstream caching plus rate limits. Valid symbol/query variation still requires a quota bound.

```ts
// Before: unknown parameters are ignored
const symbol = incoming.get('symbol');
// After: first reject unexpected input; add shared caching/rate limits too
if ([...incoming.keys()].some(k => k !== 'symbol') || incoming.getAll('symbol').length !== 1) {
  return res.status(400).json({ error: 'Invalid parameters' });
}
```

### M4 — Delayed Stripe events can overwrite current subscription state

**Locations:** `functions/src/index.ts:2960`, `functions/src/index.ts:3042`.

Subscription handlers write the incoming event snapshot into the user's entitlement without reconciling current Stripe state. The deleted handler does not check whether the event belongs to the currently stored subscription. After a user resubscribes, a delayed deletion for their previous subscription can revoke their new Pro entitlement. Event-ID deduplication does not prevent this because the events are distinct. Stripe explicitly does not guarantee delivery order. [Stripe webhook documentation](https://docs.stripe.com/webhooks).

**Fix:** Reconcile current customer subscriptions and lifetime ownership before setting entitlements. Guard old-subscription events and process reconciliation serially per customer. Use retryable event processing; a claim written before work begins also needs a lease/recovery mechanism for process termination.

### M5 — Large values silently fall back to plaintext storage

**Locations:** `src/utils/crypto.ts:74`, `src/utils/user-storage.ts:141`.

`String.fromCharCode(...combined)` passes every encrypted byte as a function argument. Large trade histories exceed the JavaScript engine's argument limit. The caller catches the failure and writes the original plaintext, contrary to the encryption-at-rest description. **Reproduced on the installed Node/V8 runtime:** 1,000 bytes succeed; 250,000 bytes throw `RangeError: Maximum call stack size exceeded`. Browser thresholds vary.

**Fix:** Encode base64 in bounded chunks; propagate encryption failure instead of silently downgrading confidentiality. Also document that a key derived solely from UID and a locally stored salt does not protect against someone who can read all browser storage.

```ts
// Before
return btoa(String.fromCharCode(...combined));
// After: bounded argument count
let binary = '';
for (let i = 0; i < combined.length; i += 8192) {
  binary += String.fromCharCode(...combined.subarray(i, i + 8192));
}
return btoa(binary);
// Separately remove the caller's plaintext fallback and surface failures.
```

### M6 — Lapsed subscribers cannot truly clear their old cloud data from Settings

**Location:** `src/pages/Settings.tsx:338`.

Clear All Data calls `clearSyncData` only when the current client considers the user Pro. A lapsed subscriber can still have an old cloud snapshot, so clearing data removes only the local copy. Upgrading later can restore it. The server already permits authenticated users to clear their own data without Pro entitlement.

**Fix:** Request cloud cleanup for every real authenticated user, independent of plan, and clearly report failure before clearing local data. Test a Pro → free → clear → Pro lifecycle.

### M7 — MetaTrader ingestion has no total storage or request quota

**Locations:** `functions/src/index.ts:5888`, `functions/src/index.ts:5907–5995`.

Any authenticated user can mint a key; repeated pushes can write up to 500 new deal documents each. There is no per-user request rate, cumulative storage/record cap, verified-email requirement, or expiry/retention enforcement in this path. The batch-size limit protects one request, not total resource consumption. An abusive account can generate arbitrary ticket IDs and grow Firestore storage/write costs indefinitely.

**Fix:** Apply an explicit product entitlement policy, per-key/user request and storage quotas, validated deal schemas and field lengths, and lifecycle cleanup. Store a hash of the bearer key where feasible.

```ts
// Before: after key lookup, immediately accept deal writes
const uid = match.docs[0].id;
// After — design sketch, backed by atomic server counters
const uid = match.docs[0].id;
await reserveIngestBudget(uid, { requests: 1, records: deals.length });
const validatedDeals = validateDeals(deals);
```

### M8 — Analytics consent does not govern Google Analytics initialization

**Locations:** `src/App.tsx:90`, `src/lib/analytics.ts:14`, `src/lib/posthog.ts:24`, `src/components/PostHogTracker.tsx:50`.

`initGA()` runs on mount, configures GA, and inserts its script whenever the tracking ID exists, without consulting the consent record or setting a denied default. The local configuration contains a GA ID. PostHog also continues explicit page/event capture under memory persistence after decline; the privacy page describes that session-only behavior, while parts of the cookie page describe usage/error tracking as consent-only. This is a concrete behavior/documentation inconsistency, not a legal determination.

**Fix:** Define one consent contract and apply it to all analytics SDK initialization, capture, identity, revocation, and documentation. If analytics must be opt-in, gate initialization and disable capture on revocation; changing persistence alone does not stop transmission.

```ts
// Before
initGA();
// After: also react to later consent changes and implement revocation
if (analyticsConsentGiven()) initGA();
```

## Dependency and engineering health

Advisory counts include development/transitive packages and overlap between lockfiles; they are **not counts of demonstrated production exploits**.

| Lockfile | Critical | High | Moderate | Low | Total |
|---|---:|---:|---:|---:|---:|
| Root | 7 | 29 | 10 | 3 | 49 |
| Functions | 4 | 19 | 12 | 3 | 38 |

Direct affected packages include `xlsx`, `jspdf`, `remotion`/`@remotion/player`, `react-router-dom`, `dompurify`, `vite`, `vitest`, and backend Firebase packages. Critical transitive findings include `protobufjs`; the backend `next` findings originate from the email preview dependency, not a production Next.js application. The jsPDF advisory APIs were not found in the reviewed report generator. DOMPurify advisory configurations were not established as reachable through the shared markdown renderer. These distinctions matter when prioritizing updates.

Preserved raw npm results: [root advisories](audits/2026-09-10/npm-audit-root.json), [Functions advisories](audits/2026-09-10/npm-audit-functions.json). Review each update and its reachable surface; some npm suggestions change major versions or suggest older package releases. Do not blindly run `npm audit fix --force`.

Additional engineering observations:

- **Lint is not a usable clean gate yet.** Many errors concern explicit `any` and unused code; warnings include React hook dependencies. Establish a passing baseline without blanket disabling meaningful checks.
- **Backend integration coverage is missing from the exposed scripts.** Functions has a build script but no test script; the browser harness covers one component interaction. Add Firebase Rules/emulator tests and Stripe lifecycle tests around the findings above. No tracked `.github` workflow exists; external CI configuration was not inspected.
- **Sync polls full snapshots every ten seconds.** `getSyncData` reads 11 manifests plus chunks for every poll, even when unchanged. At one open tab this is 360 calls and at least 3,960 manifest reads per hour, before user-document reads and chunks. Consider revisions/change cursors or subscriptions after correctness is fixed.
- **Bundle and cache weight need a measured performance pass.** The built main chunk is 628.87 kB / 194.71 kB gzip; Firebase is 512.39 / 154.28 kB; icons are 394.52 / 86.99 kB. Workbox precaches 192 entries totaling about 7.75 MiB. Lazy imports already exist, but broad precaching still downloads optional assets. These are build measurements, not measured Core Web Vitals.
- **CSS minification reports malformed syntax.** Trace the reported generated-CSS warnings back to source before considering the build warning-free. No visual regression was attributed to them in this audit.
- **Unused poll rules remain permissive.** `firestore.rules:26` lets any authenticated user replace the entire `votes` field without validating counts or coupling it to their vote record. No current client poll usage was found. Remove retired rules, or implement a validated server-side voting transaction before reusing the feature.

## Controls that are already present

Private user documents and sync data are owner-readable and client-write-denied. Stripe checkout uses a server price allowlist and verified webhook signatures; Pro-only server features check server-owned entitlement data. AI quota counters use server transactions. Admin checks require verified email. Shared markdown output is sanitized. Storage screenshot paths enforce ownership, image size/type, and a server-owned Pro flag. Production header configuration includes CSP and standard transport/framing protections. Secret-bearing local environment files are ignored, and sourcemap stripping is implemented in the normal build script.

These are code-level observations; deployed configuration parity was not verified.

## Evidence and repair order

The four sync reproductions assert the observed buggy behavior, rather than pretending it is correct behavior. Source is preserved as [a non-discovered test text file](audits/2026-09-10/sync-reproduction.test.ts.txt), with [execution output](audits/2026-09-10/sync-reproduction.log). The temporary executable test was removed so it does not become part of the normal test suite. Convert the cases to desired-behavior regression tests when fixing sync.

1. Remove auth credentials from all telemetry; repair save ordering and deletion semantics together.
2. Make billing/data deletion durable and complete; scope local screenshot cleanup by user.
3. Restrict push destinations and bound ingestion/proxy resource usage; replace the vulnerable spreadsheet parser.
4. Reconcile Stripe events against current state, fix retry/encryption/consent behavior, then update dependencies with focused regressions.
5. Establish meaningful CI checks and measure authenticated/mobile performance and accessibility in a dedicated browser pass.
